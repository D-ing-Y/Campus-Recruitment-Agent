### 2026-08-14 简历上传 500 检修

故障运行证据表明 PDF 已完成归档、文本提取和质量检查，失败点位于模型结构化
简历草稿。当 provider 返回可解析但不符合 Pydantic 契约的 Tool 参数时，provider 层提前
抛错，绕过了共享的一次有界纠错重试；同时失败收口写入了不在 `ErrorEvent` 枚举中的
错误类型，导致错误记录、Run 终态和 Session `latest_run_id` 都未更新，Web 最终只能返回 500。

修复后：

- provider 保留无效原始 Tool 参数，交给共享结构化边界执行最多一次纠错重试。
- 简历 v3 prompt 明确七个根字段和 text block 契约。
- 对真实模型中已观察的无损别名执行确定性归一化，仅改字段名或删除重复别名，
  不补写、不推断简历内容；未知额外字段仍被拒绝。
- 结构错误返回 PII-safe `502 llm_invalid_output`，供应商不可用返回 PII-safe 503。
- 失败 Run 收口为 `failed/inspect.run`，记录 LLM receipt 和脱敏错误，Session 保持可重试。

后续检查发现生产 Runtime 使用的延迟模型代理只转发普通生成，没有公开 capability 或
转发结构化生成，导致共享结构化边界把真实 DeepSeek 误记为 legacy JSON provider。修复后
代理在不加载网络 SDK 的前提下公开 capability，并在第一次真实结构化调用时转发输出模型；
DeepSeek `auto` 解析出的 Tool Calling 作为显式策略下发，不允许在简历抽取中静默回退 JSON。

## 3. 验收用例结果

### 完整简历路径

1. HTTP 创建固定 `local-web-user` Session。
2. multipart 上传文本 PDF，Resume workflow 返回 `interrupted`。
3. Web 读取 review view 并依次提交全部确认。
4. Session current refs 得到 confirmed ResumeEvidence，next action 为 `candidate.build`。
5. Candidate build 完成并返回可展示的 immutable Candidate ProfileSnapshot。

### 信息不足与恢复路径

1. 上传缺少个人责任边界的匿名 PDF。
2. Candidate build 返回 `interrupted` 和 `answer_questions`。
3. Web 提交当前 question ID 的回答。
4. 回答先被证据化，Graph 恢复后产生后继画像并完成。
5. 对 Resume response 和 Candidate response 进行同 ID 重放，均返回 `deduplicated=true`，
   Candidate profile history 数量不增加。

## 4. 安全与架构检查

- 服务端固定本地身份，不接受客户端权威 owner/candidate ID。
- Resume build 只读取 Session current confirmed ResumeEvidence。
- 仅接受允许的扩展名、MIME 和 10 MB 上限。
- 服务端生成上传路径，完成后清理；错误 envelope 不包含绝对临时路径。
- 前端只保存 Session ID，业务状态仍在现有 SQLite/BlobStore/checkpoint。
- evaluator、question planner 和 LLM provider 仍位于现有可替换端口之后，Web 不依赖具体实现。
- 2026-08-14 检修修改了共享 LLM 结构化边界、Resume 失败收口和简历输出契约兼容层；
  未改动 Candidate 充分性评估、追问计划或画像生成规则。
