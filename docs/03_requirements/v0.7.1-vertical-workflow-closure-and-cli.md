## 1. 背景

v0.3-v0.7 已分别实现 Evidence Pipeline、CandidateProfileGraph、RoleProfileGraph、
ProfileMatchingGraph、PreparationPlanGraph、FeedbackGraph 和一个本地 FeedbackReplanSaga；当前
离线回归基线为 338 项测试通过。这些结果证明既定 schema、确定性 policy、repository、Graph
路由、checkpoint 和部分 saga 行为已经具备，但尚不能证明真实用户流程已经闭环。

当前已确认的产品断点包括：

- `campus-agent run` 仍只执行旧 Mini Runtime 和 mock job search，不调用 v0.4-v0.7 业务子图；
- 业务子图没有统一的运行装配层、Run/Session、产物目录、节点事件和 `inspect` 入口；
- Candidate 真实 DeepSeek 输出可产生引用合法但 predicate 不可投影的 Claim，离线 mock 未暴露该问题；
- 缺少 CareerIntent 首次采集、确认和 snapshot 入口；
- 缺少 PreparationConstraints 首次创建入口；
- Matching 和 Feedback 返回的 typed directive 缺少通用 application service 消费者；
- 当前固定集 Eval 中部分用例验证的是 metric/schema contract，而不是从真实 Graph 产物计算语义质量；
- Role 的真实来源验收不能用本地 JD 或 fixture 代替，并且必须保留授权、风控和 raw-first 边界。

v0.7.1 用于修复这些“独立实现已存在，但真实流程不可运行、不可诊断或语义不可靠”的问题。

## 2. 版本定位

v0.7.1 是 v0.7 的纵向加固版本，不是新业务功能版本，也不是 v1.0 Parent Graph。

本版本采用：

```text
共享 CLI / RunSession / Application Service
  → 按依赖顺序调用现有 subgraph
  → 每一步产生不可变业务对象、checkpoint 和诊断产物
  → 人工门通过 CLI interrupt/resume
  → 跨图动作通过 typed handoff/directive 消费
```

完成后，用户应能通过一组连续、可恢复的 CLI 命令完成真实流程；各子图仍保持独立 State、
checkpoint 和 repository 边界。v1.0 再把同一组已验收边界组合为统一 LangGraph Parent Graph。

## 3. 目标

1. 建立默认交互式、同时支持 one-shot 与 `--json` 的正式 CLI。
2. 建立统一 RunSession、runtime factory、运行产物和节点级可观测契约。
3. 按依赖顺序逐层检测并修复每个子 Workflow，真实失败必须能定位到具体层和节点。
4. 使用真实简历 PDF、用户当前已准备的可选项目材料、明确求职意图和用户授权的
   DeepSeek 完成 Candidate/Intent 验收。项目 README 未准备好时可明确省略，不得改用开发记录或模型
   推测补齐项目经历。
5. Role 验收不使用本地 JD，使用 opt-in 真实来源并诚实保留 auth/risk/adapter 阻塞状态。
6. 让 Candidate、Intent、Role、Matching、Decision、Preparation、Feedback 能通过 application
   service 和 typed handoff 连通。
7. 将 Eval 从“预填结果/布尔清单聚合”升级为可从真实 Graph 产物计算的验收。
8. 验证进程重启、重复提交、部分失败、stale snapshot 和预算终止。

## 4. 非目标

- 不在 v0.7.1 实现统一 LangGraph Parent Graph。
- 不实现 v0.8 Hybrid RAG、向量检索或长期记忆。
- 不实现 Web/桌面 UI、FastAPI、分布式 worker、PostgreSQL、对象存储或 Multi-Agent；允许实现
  项目专用 CLI UI 外壳，但不得成为第二套业务实现。
- 不实现自动投递、自动登录、验证码绕过、反爬绕过或风险控制规避。
- 不用 fixture、本地 JD、首页可访问或 schema 解析成功冒充真实来源/真实语义验收。
- 不把 CLI application service saga 表述为 v1.0 Parent Graph。
- 不把真实简历、招聘 raw、Cookie、API key 或个人敏感运行产物提交到 Git。

## 5. 统一纵向闭环定义

每个 Workflow 必须依次通过九层门禁：

| 层级 | 检查对象 | 放行条件 |
| --- | --- | --- |
| L1 契约层 | schema、版本、owner、ID/ref、状态枚举 | 非法输入在副作用前拒绝，跨模块语义有文档依据 |
| L2 证据层 | Artifact、Fragment、locator、raw-first | 所有事实可回溯，原始写入失败时停止解释 |
| L3 模型层 | prompt、provider、原始 structured output、重试/cache | 保存安全 receipt；模型输出不能越过权限或确定性 policy |
| L4 Validator 层 | 引用、领域 predicate、authority、scope、causality | 接受/拒绝均有稳定 reason code，不可消费对象不进入投影 |
| L5 投影/策略层 | Profile、Gap、排序、计划、影响路由 | 只消费已验证对象；unknown 与 failed 分离；确定性结果可重放 |
| L6 持久化层 | repository、事务、版本、幂等、stale/supersede | 重复执行零重复写；失败不发布半成品 |
| L7 Graph 层 | node、route、loop、budget、interrupt/resume | 所有合法分支可达、可终止、可跨进程恢复 |
| L8 CLI/可观测层 | 提示、状态、inspect、report、退出码 | 用户能理解下一步；开发者能定位到失败层和对象 ID |
| L9 Eval 层 | fixture、真实模型、真实来源、failure/replay | Graph 产物驱动指标；真实与离线结果分层陈述 |

任一层未通过，该 Workflow 不得标记纵向闭环，也不得仅凭最终命令退出码为 0 放行。

## 6. 工作包与依赖顺序

### WP0：共享运行基座、CLI 和可观测性

交付：

- 统一 runtime factory，装配 BlobStore、Evidence/Profile/Domain repositories、LLM provider、
  SourceAdapter registry 和 SQLite checkpointer；
- `RunSession`、`RunManifest`、`NodeEvent`、`LLMCallReceipt`、`ErrorEvent`、`ArtifactIndex`；
- 默认交互式 CLI、one-shot 子命令、`--json` 和稳定退出码；
- `doctor`、`session start/status/resume/history` 与 `inspect`；
- 统一 `data/runs/<run_id>/` 产物，并对敏感内容脱敏；
- 修复 trace 固定 success/零时长、节点输出计数读取旧 state 等不可诊断行为。

WP0 只提供横向运行骨架，不改变各业务图的事实语义。

### WP1：Evidence 与 CandidateProfileGraph

真实输入至少包含用户授权的简历 PDF；项目 README 是可选的增量证据。用户尚未准备好对外项目
介绍时，CLI 必须允许只提供简历，并使项目经验维度保持缺失/未知，不读取未授权的仓库
README，也不影响简历已支持字段的 Candidate E4 验收。

必须验证：

```text
local material
  → Artifact
  → Fragment + locator
  → DeepSeek structured claim candidate
  → candidate-domain predicate validation
  → validated Claim
  → CandidateProfile snapshot
  → sufficiency/unknown
  → CLI ask/upload/correct/skip/cancel
```

必须修复 Candidate predicate 契约、结构化输出约束、领域 Validator、Projector 与 record identity
的一致性。引用合法但无法被 CandidateProfile 消费的 Claim 不得静默写入 active claim set。

### WP2：CareerIntent 首次入口

新增最小 intake/application service 边界：

```text
raw user intent
  → archived user evidence
  → structured CareerIntent candidate
  → hard/negotiable/preference classification
  → CLI confirmation
  → versioned CareerIntent snapshot
  → SearchScope projection
```

“工作地点必须成都”必须保存为硬约束；“优先大型企业和互联网科技公司”是偏好，不得错误升级为
硬资格。普通偏好修改只 rematch，SearchScope 变化才触发 Role 重检索。

### WP3：RoleProfileGraph 真实来源

不使用本地 JD，使用确认后的 CareerIntent/SearchScope 发起 opt-in live source 运行：

```text
query planning
  → recruitment discovery raw archive
  → normalization/dedup
  → official verification raw archive
  → JobIdentityLink/FieldResolution
  → experience raw archive
  → role Claim validation
  → JobInstanceRoleProfile
  → RoleFamilyProfile
  → coverage/unknown/auth route
```

登录、验证码、限流、风险控制、来源变化或未知站点必须形成结构化阻塞结果；不得绕过或伪造成功。

### WP4：ProfileMatchingGraph 与 TargetDecision

只消费 WP1-WP3 真实产生的 current snapshot：

- 分离 hard qualification、capability/evidence coverage、preference conflict 和 epistemic uncertainty；
- 所有数字、权重、排序和 route 由确定性代码负责；
- LLM explanation 必须通过 fact/citation/action validator；
- CLI 展示比较并收集 select/defer/reject/revise/refresh/cancel；
- candidate/intent/role 变化产生 typed handoff，不直接跨域覆盖。

### WP5：PreparationConstraints 与 PreparationPlanGraph

新增 PreparationConstraints 首次创建/确认入口，再验证：

```text
selected TargetDecision
  → exact snapshot validation
  → objectives/activities
  → deterministic priority factors
  → MinimumPreparationPackage
  → capacity/dependency/deadline schedule
  → LearningPlan
  → CLI review/revise/defer/cancel
```

不得为不可处理资格生成虚假任务，不得把 package status 表达为 Offer readiness。

### WP6：FeedbackGraph 与跨图 directive

先验收 FeedbackGraph raw-first、归因确认和影响路由，再由 application service 消费 directive：

```text
Feedback raw
  → Observation
  → Diagnosis candidate
  → Attribution confirmation
  → feedback_signal Claim / progress
  → Impact
  → Directive
  → resolved successor snapshot refs
  → rematch
  → replan
```

除现有 candidate rebuild saga 外，还必须覆盖 intent review、role instance refresh、role family
aggregation candidate、rematch 和 replan 的合法边界。单次事件不得直接改写 RoleFamilyProfile。

### WP7：CLI 串联验收

在不引入 Parent Graph 的前提下，通过同一 RunSession 串联：

```text
Candidate + Intent
  → Role research
  → Matching + TargetDecision
  → Preparation
  → Feedback
  → successor snapshot
  → Rematch + Replan
```

用户既可逐命令执行，也可由交互式 CLI 根据 session 当前状态提示下一步。Application service 只保存
引用和 handoff 状态，不复制各子图的可变业务 State。

## 7. CLI 功能要求

### FR-CLI-01 交互模型

- `campus-agent` 无子命令时进入交互式引导。
- 所有核心操作同时提供 one-shot 子命令，便于测试、脚本和 Agent 调用。
- 所有只读/执行命令支持 `--json`；JSON stdout 不混入装饰文本。
- 交互提示必须展示当前 workflow、节点结果、下一动作和可检查路径。

### FR-CLI-02 命令域

首版命令域至少包括：

```text
doctor
session start | status | resume | history
candidate build | resume | show | diff
intent create | revise | show
role research | resume | show
match run | resume | show
target list | select | defer | reject
constraints create | revise | show
plan build | resume | show
feedback add | resume | show
inspect run | node | llm | evidence | claims | profile | handoff
```

### FR-CLI-03 状态与退出码

- 业务状态与进程退出码分离；`interrupted`、`blocked_by_auth`、`partial`、
  `completed_with_unknowns` 可以是成功保存状态。
- 参数/契约错误、权限错误、外部依赖错误和内部错误使用稳定退出码。
- 每次命令输出 `run_id`、`session_id`、status、next_action 和 artifact/report 路径。

### FR-CLI-04 CLI UI 与 Model Provider 配置

- `campus-agent` 在真实 TTY 中进入项目统一 CLI UI；非 TTY 保持不会阻塞的引导输出。
- CLI UI 先建立可扩展首页和配置域，本阶段只开放 Model Provider 管理；未开放域必须明确标记 unavailable。
- Add Provider 的 preset 属于枚举选择，必须由用户显式输入，不提供默认占位值。
- Provider ID、显示名和预设 endpoint/model 使用 `Label : dim-default` 行内浅色占位值；直接回车
  接受默认值，首个非空输入必须先清除整段占位值再显示用户输入。Provider ID 必须按 preset 自动生成
  并避开已有 ID。
- 所有布尔确认统一采用 Linux 风格 `[Y/n]` 或 `[y/N]`；回车选择大写项，不使用浅色占位值。
- Model Provider 同时提供 one-shot：`model add/edit/list/show/use/remove/test`，交互层调用同一 service。
- Provider 记录采用 CC Switch 风格的 `id/name/settingsConfig/category/websiteUrl/createdAt/sortIndex/
  notes/icon/iconColor/isCurrent` 形状，以 SQLite 为 SSOT，并用事务原子切换 current。
- `settingsConfig` 只保存 provider、base URL、model、运行参数和 `credential_ref`；不得保存 API key。
- API key 通过隐藏输入或 stdin 导入 Git 忽略且权限为 `0600` 的本地 SecretStore；参数、stdout、JSON、
  doctor、Run artifact、checkpoint 和异常不得出现 key。
- current Provider 不得删除；至少保留内置 mock Provider，避免删除配置后正式 CLI 不可启动。
- 不自动读取 `.env`。自动化可继续显式使用进程环境变量；普通本地运行默认解析 active Provider。
- DeepSeek 预设使用官方 OpenAI-compatible endpoint/model 标识；预设值必须可在 UI 中确认和覆盖。
- DeepSeek 结构化业务请求的 timeout 默认 90 秒，并可在 add/edit/CLI UI 中覆盖；健康检查仍使用更小上限。
- Provider timeout、rate limit、auth 和通用 provider failure 必须保持各自错误类型，不能统一伪装为
  `llm_output_error`；外部依赖错误通过 CLI exit 4 暴露。

## 8. 运行产物与诊断要求

每次 run 至少形成：

```text
data/runs/<run_id>/
  run_manifest.json
  events.jsonl
  state.json
  llm_calls.jsonl
  errors.jsonl
  artifact_index.json
  handoffs.jsonl
  report.md
```

- `events.jsonl` 是节点/工具/路由/人工门的追加事件流；
- `state.json` 是安全摘要，不是 Evidence Store 或 checkpoint 的替代；
- 原始文件和完整网页正文继续保存在 BlobStore；
- 业务事实继续保存在 Evidence/Profile/Domain repository；
- checkpoint 只保存执行状态；
- CLI `inspect` 读取稳定契约，不要求用户直接解析 SQLite msgpack；
- 所有文件默认位于 Git 忽略目录，禁止写入 secret、Cookie 或完整私人正文。

## 9. 测试与 Eval 要求

每个 WP 必须依次通过：

1. schema/contract/unit；
2. repository/side-effect；
3. single-node；
4. subgraph route/loop；
5. interrupt/resume/checkpoint；
6. CLI subprocess；
7. failure injection 与 replay；
8. opt-in DeepSeek semantic smoke；
9. Role 专属 opt-in live source smoke；
10. 用户真实案例人工复核。

真实材料只能作为本地 opt-in 数据，不进入 Git；可提交回归数据必须是脱敏最小快照或合成等价结构。

## 10. 验收标准

v0.7.1 只有同时满足以下条件才可标记 Implemented / Accepted：

1. Requirements、RFC、ADR、CLI/Run contract、Tasks 和 Eval report 已同步。
2. 正式 CLI 不再把旧 Mini Runtime mock 成功表述为业务流程成功。
3. 每个 Workflow 九层门禁均有实际结果、证据路径和失败案例。
4. 真实 DeepSeek Candidate 画像不再出现“Claim 已保存但全部不可投影”的静默失败。
5. CareerIntent 与 PreparationConstraints 均可通过 CLI 首次创建、确认、版本化和修改。
6. Role 使用非本地 JD 的真实来源完成一次受边界约束的 live smoke，或诚实记录阻塞而不伪造完成。
7. Matching、Decision、Preparation 和 Feedback 均消费真实上游产物，不使用测试手工 seed 作为最终验收。
8. 至少一条反馈完成 evidence → successor snapshot → rematch → replan 的可追溯链。
9. 每个人工门均可跨进程 resume，重复响应/事件零重复业务写入。
10. 每个节点真实记录成功、失败、耗时、route、输入/输出 refs 和安全错误摘要。
11. 全量回归继续通过；真实语义 Eval 从 Graph 产物计算，不以预填 predicted/boolean 替代。
12. 新增 `docs/07_evaluation/v0.7.1-eval-report.md` 后才允许标记 Implemented / Accepted。

## 11. 实现顺序

严格按以下顺序推进，每个工作包通过放行门后才进入下一项：

1. WP0 CLI/RunSession/可观测基座；
2. WP1 Evidence + Candidate；
3. WP2 CareerIntent；
4. WP3 Role live source；
5. WP4 Matching + Decision；
6. WP5 Constraints + Preparation；
7. WP6 Feedback + typed directive；
8. WP7 CLI 串联真实 E2E；
9. Eval report、README/Roadmap/version 与提交收口。

实现中发现跨模块契约缺口时必须先更新 v0.7.1 文档，不得回写 v0.3-v0.7 历史文档来伪造连续性。
