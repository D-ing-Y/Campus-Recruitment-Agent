# v0.6 双画像匹配与用户决策需求

状态：Implemented / Accepted
日期：2026-07-22
关联 ADR：`docs/05_adr/0006-separate-eligibility-coverage-and-preference.md`
关联 RFC：`docs/04_rfc/0006-profile-matching-and-user-decision.md`

## 1. 背景

v0.4 已生成可追溯、可纠正的 `CandidateProfile`，v0.5 已生成经过第三方发现、
企业官网核验和经验信号补充的 `JobInstanceRoleProfile` / `RoleFamilyProfile`。v0.6
需要把两个画像与独立的 `CareerIntent` 放在同一决策边界中，帮助用户判断：

- 是否明确满足岗位的硬性资格；
- 岗位要求中有多少已被候选人证据覆盖；
- 缺少的是能力、证明材料，还是信息本身仍未知；
- 岗位与用户偏好有哪些冲突；
- 用户应纠正画像、调整目标、刷新岗位，还是选择/暂缓/拒绝岗位。

这个阶段不能退化为“让 LLM 给一个匹配百分比”。资格、能力证据和偏好属于不同语义，
未知也不等于不具备。v0.6 必须使用确定性规则生成可审计比较事实，LLM 只解释这些事实，
用户负责最终目标选择。

## 2. 目标

实现以下可恢复闭环：

```text
CandidateProfile snapshot
CareerIntent snapshot
JobInstanceRoleProfile snapshot(s) + optional RoleFamilyProfile context
  → 校验输入版本、归属和新鲜度
  → 硬性资格逐项判定
  → 能力要求与候选人证据逐项对齐
  → 确定性计算证据覆盖度
  → 识别四类 gap
  → 生成可引用的岗位比较结果
  → 用户决策 interrupt
      ├─ 选择 / 暂缓 / 拒绝目标 → 保存决策
      ├─ 纠正候选人事实 → 请求 v0.4 重建 → 重新比较
      ├─ 调整普通偏好 → 新 CareerIntent → 重新比较
      ├─ 调整 SearchScope → 请求 v0.5 重检索 → 重新比较
      └─ 岗位过期/存疑 → 请求 v0.5 刷新 → 重新比较
```

## 3. 范围

### 3.1 必须实现

- 独立 `profile_matching` LangGraph subgraph，不提前实现 v1.0 Parent Graph。
- `MatchingInputSet`、`RequirementAssessment`、`GapAssessment`、`ComparisonSet`、
  `TargetDecision`、`RebuildDirective` 契约。
- `CareerIntent` v0.6 结构化 constraint 与 legacy 字符串偏好迁移/确认边界。
- 以具体岗位画像为主要决策对象；岗位族画像只提供市场背景和迁移价值上下文。
- 硬性条件状态与能力证据覆盖度完全分离。
- 能力差距、证据差距、偏好冲突、认知不确定性四类 gap。
- 由确定性代码完成资格比较、等级比较、权重、分子、分母、覆盖度和排序键计算。
- 每个判定引用候选人 Claim、岗位 Claim 和输入 snapshot ID；无法引用时保持 unknown。
- LLM 结构化解释器只能解释已计算事实，不能修改状态、权重、覆盖度或差距类型。
- 多岗位比较使用可解释的稳定排序策略，不生成不透明综合分。
- `review_comparison` interrupt 与 select/defer/reject、revise_candidate、revise_intent、
  refresh_role、cancel 动作。
- 候选人纠正、偏好调整和岗位刷新只产生结构化重建请求，不跨边界直接修改其他画像。
- SearchScope 影响分析：普通可协商偏好变化只重算匹配；目标岗位、城市、行业、公司范围、
  毕业年份或招聘类型等检索边界变化才请求 v0.5 重检索。
- snapshot 失效、重复 resume、进程重启、循环预算、trace、报告和 eval。
- 保留 v0.1-v0.5 全量回归。

### 3.2 比较层次

- `JobInstanceRoleProfile` 是硬性资格、申请目标和用户决策的唯一主对象。
- `RoleFamilyProfile` 可提供岗位族常见能力、样本分母和经验信号背景，但不能覆盖具体岗位的
  官方要求，也不能单独产生“可投递”结论。
- 一个 matching run 接收一个 candidate snapshot、一个 intent snapshot、1..N 个当前
  job instance snapshot 和 0..N 个 family context snapshot。
- 每个岗位独立生成 `GapAssessment`；`ComparisonSet` 只组合和排序这些结果。

### 3.3 四类 Gap 的边界

1. `capability_gap`
   - 岗位存在可映射的能力要求；
   - 候选人有相关能力事实，但已确认等级低于要求，或有明确证据表明尚未具备；
   - “候选人画像中没有这项能力”本身不能直接证明 capability gap。
2. `evidence_gap`
   - 候选人声明或画像推断可能具备能力；
   - 但责任边界、成果、熟练度、时效性或 Claim 权威不足以覆盖岗位要求。
3. `preference_conflict`
   - 岗位事实与 `CareerIntent` 的 hard constraint 或 negotiable preference 冲突；
   - 必须标明 `hard` 或 `negotiable`，不得反向改写 CandidateProfile。
4. `epistemic_uncertainty`
   - 候选人事实、岗位要求、能力映射或来源新鲜度缺失、模糊、过期或冲突；
   - unknown 不进入能力覆盖分子的成功项，也不得作为明确失败项。

### 3.4 非目标

- 不预测 Offer、面试通过率、薪资结果或“上岸概率”。
- 不生成单一、不可解释的综合匹配分，也不把覆盖度命名为成功率。
- 不在 v0.6 生成学习路线、准备计划、面试题或自动投递；这些属于 v0.7 以后。
- 不重新实现招聘爬虫、候选人材料摄取或 v1.0 Parent Graph。
- 不直接修改 CandidateProfile、RoleProfile 或历史 CareerIntent snapshot。
- 不让用户把未经证据化的纠正直接写入画像事实。
- 不让 LLM 决定硬性资格、权重、分母、排序或 Graph 路由。
- 不引入 RAG、向量索引、分布式存储、Multi-Agent 或 Web UI。

## 4. 输入与输出

### 4.1 输入

- `run_id`、`thread_id`、`user_id`。
- `candidate_profile_snapshot_id`。
- `career_intent_snapshot_id`。
- 1..N 个 `job_instance_profile_snapshot_ids`。
- 可选的 `role_family_profile_snapshot_ids`。
- matching、explanation、interaction 和 rebuild 循环预算。
- resume 时的结构化 `HumanInteractionResponse`，不包含未经授权的文件正文或秘密值。

### 4.2 输出

- 每个具体岗位一个不可变 `GapAssessment` snapshot。
- 一个 `ComparisonSet`，包含稳定排序、推荐分层和所有输入版本。
- 0..N 个 `TargetDecision`；决策与画像分开存储。
- 可选 `RebuildDirective`：`candidate_profile_required`、`role_research_required`、
  `role_refresh_required` 或 `rematch_required`。
- Graph 状态：`completed`、`completed_with_unknowns`、`interrupted`、`reroute_required`、
  `cancelled` 或 `failed`。
- trace、LLM/tool 调用摘要、预算消耗、stale 原因和最终报告。

## 5. 功能要求

### FR-01 输入与快照校验

- 所有 snapshot 必须存在、属于当前 user/owner，并通过对应 schema 校验。
- 具体岗位画像的 `source_status`、freshness 和 unresolved conflict 必须进入比较输入。
- 一个 assessment 必须固定引用 candidate、intent、job instance 和可选 family snapshot ID。
- 输入 snapshot 在运行中被新版本替代时，当前 assessment 标记 `stale`，不得原地换引用。
- job instance 缺失、过期或身份模糊时仍可输出 unknown/refresh directive，不得假装完成匹配。

### FR-02 硬性资格判定

- 每个 `Qualification(importance=hard)` 独立生成判定。
- 状态至少包括：`passed`、`failed`、`unknown`、`conflicted`、`not_applicable`。
- `failed` 必须同时有可比较的候选人事实、岗位事实和确定性 operator 结果。
- 候选人事实缺失、岗位字段缺失或 operator 不支持时为 `unknown`，不能默认失败。
- 总体 `hard_constraint_status`：任一明确失败为 `failed`；无失败但存在 unknown/conflict 为
  `unknown`；全部适用项通过才为 `passed`。
- 不支持的自然语言 hard constraint 进入 uncertainty，并可请求用户确认。

### FR-03 能力对齐与等级比较

- 优先按 canonical `capability_id` 对齐；raw label 只可形成待确认 mapping。
- 岗位 `core_capability`、`bonus_capability` 分开计算；职责和 work context 默认只作解释，
  除非契约明确映射为能力要求。
- 候选人 `status=conflicted/unknown` 或 `level=unknown` 不得判为能力已满足。
- 等级次序和 operator 由版本化确定性 policy 定义。
- 可迁移能力只能以显式 ontology relation 参与，且输出 transfer reason 与折减后的确定性权重；
  LLM 不得自由声称技能等价。

### FR-04 可解释覆盖度

- 每个岗位输出核心能力与加分能力两个覆盖明细，不输出 Offer 概率。
- 首版核心能力覆盖公式：

```text
eligible_weight = sum(weight of assessable core requirements)
covered_weight = sum(weight of core requirements with outcome=satisfied)
core_evidence_coverage = covered_weight / eligible_weight
```

- `unknown`、unmapped 和 conflicted requirement 不进入 `eligible_weight`，但必须进入
  `uncertain_weight` 和 uncertainty 列表；报告同时展示总要求权重，防止高 unknown 时覆盖度虚高。
- requirement weight 只来自版本化规则：importance、obligation 和岗位来源权威；模型不能改权重。
- 必须输出分子、分母、排除项、policy version 和逐项贡献，不只输出百分比。
- 若 `eligible_weight=0`，coverage 为 null，不能输出 0 或 100%。

### FR-05 偏好兼容性

- 确定性比较只消费 v0.6 structured constraint；legacy 字符串必须先解析为待确认项并由用户确认。
- `CareerIntent.constraints(kind=hard)` 与岗位可结构化字段逐项比较；明确冲突可阻塞推荐但不等同资格失败。
- `constraints(kind=negotiable)` 逐项输出 `aligned`、`conflict`、`unknown`、`not_applicable`。
- 薪资、城市、行业、公司类型等只有在双方值和单位均可比较时才判定；否则 unknown。
- 偏好结果不参与能力覆盖分子/分母。
- hard preference conflict 和 negotiable conflict 必须在 UI/report 中分栏。

### FR-06 GapAssessment 与证据追踪

- 每个 requirement/qualification/preference assessment 必须保存双方 supporting Claim ID。
- 每个 GapItem 保存类型、严重度、依据、影响、可执行动作和置信度。
- 严重度由规则生成；LLM 只能改写解释文本，不能升级/降低严重度。
- assessment 保存 deterministic facts canonical hash；解释输出必须引用这些 fact IDs。
- 没有引用的解释句不得呈现为事实。

### FR-07 多岗位比较与排序

- 排序采用稳定的字典序，不折叠为单分：
  1. hard status：passed → unknown → failed；
  2. hard preference blocking conflict 数量少者优先；
  3. core evidence coverage 高者优先；
  4. epistemic uncertainty weight 低者优先；
  5. stable job profile ID 作为 tie-breaker。
- failed 岗位仍保留在结果中并展示失败依据，不静默删除。
- family context 只用于解释“岗位特异/岗位族常见”，不改变具体岗位的排序事实。
- `recommended_tier` 只能是 `review_first`、`needs_clarification`、`blocked`，用户仍负责选择。

### FR-08 LLM 解释边界

- 模型输入只包含已校验的 comparison facts、必要的 evidence summary 和允许动作枚举。
- 输出必须符合 `MatchExplanation` schema，并通过 fact/citation/action validator。
- 模型不得输出新的资格状态、覆盖数字、权重、GapType、Offer 概率或未经允许的动作。
- 模型不可用或校验失败时使用确定性模板，Graph 仍可完成。
- 真实 DeepSeek 调用作为 opt-in smoke，与默认离线验收分开报告。

### FR-09 用户决策 interrupt

- 比较完成后可生成 `review_comparison` request，一次 request 固定引用一个 ComparisonSet。
- 允许动作：`select_targets`、`defer_targets`、`reject_targets`、`revise_candidate`、
  `revise_intent`、`refresh_role`、`confirm_and_finish`、`cancel`。
- select/defer/reject 必须包含 job profile ID、decision status 和可选 reason code。
- response 中的 job ID、snapshot ID 和 action 必须属于当前 request。
- 重复 resume 不重复创建 TargetDecision 或新 snapshot。

### FR-10 纠正与回退边界

- `revise_candidate` 生成候选人纠正/补证请求，交由 v0.4 证据化并重建；v0.6 不直接改画像。
- `revise_intent` 先生成新的 CareerIntent snapshot，再由确定性 impact analyzer 比较 SearchScope：
  - SearchScope 未变化 → `rematch_required`；
  - SearchScope 变化 → `role_research_required`，包含新 scope 和受影响 target IDs。
- `refresh_role` 生成 `role_refresh_required`，交由 v0.5 核验/重建指定岗位。
- 回退完成后启动新的 matching run 或受控循环，旧 ComparisonSet 标记 superseded/stale。
- 普通偏好变化绝不能创建 Candidate Claim；目标范围变化也不能直接改 RoleProfile。
- SearchScope fingerprint 必须复用 v0.5 projector，不在 matching 中实现第二套 scope 算法。

### FR-11 Checkpoint、幂等与预算

- 使用 SQLite checkpointer，所有 interrupt 必须可跨进程恢复。
- assessment、comparison、decision、directive 和 response 使用稳定幂等键。
- 每个 thread 同时最多一个 pending interaction。
- 默认预算：`max_match_rounds=3`、`max_explanation_calls=10`、
  `max_decision_interrupts=3`、`max_targets=20`。
- 达到预算后保留已计算结果和 unknown，以 `completed_with_unknowns` 或
  `reroute_required` 结束，不无限循环。

### FR-12 Trace、报告与隐私

- trace 记录 snapshot IDs、规则版本、计数、路由、stale 原因和动作，不记录完整私人材料。
- 报告必须分栏展示硬性资格、核心能力覆盖、加分能力、偏好、unknown 和 evidence refs。
- 报告醒目标注“覆盖度不是 Offer 概率”。
- 用户决策原因默认只保存结构化 reason code 和用户主动提供的简短说明。
- Candidate/Role Claim 正文继续由 Evidence Store 按 owner 权限读取。

## 6. Graph 行为

```text
START
  → initialize_matching_run
  → load_and_validate_snapshots
  → evaluate_hard_qualifications
  → align_capability_requirements
  → compute_deterministic_coverage
  → evaluate_preferences_and_uncertainty
  → build_gap_assessments
  → build_comparison_set
  → explain_comparison
  → route_matching_next_action
      ├─ review_user → plan_decision_interaction
      │                 → interrupt_for_decision
      │                 → validate_and_archive_decision
      │                 → route_user_decision
      │                     ├─ persist_target_decisions → finalize
      │                     ├─ candidate_profile_required → finalize_reroute
      │                     ├─ rematch_required → initialize_matching_run
      │                     ├─ role_research_required → finalize_reroute
      │                     ├─ role_refresh_required → finalize_reroute
      │                     └─ cancel → finalize
      ├─ complete → finalize
      ├─ complete_with_unknowns → finalize
      └─ fail → finalize
```

v0.6 subgraph 不直接调用 v0.4/v0.5 subgraph；它通过 `RebuildDirective` 建立清晰的父图边界。
仅 `rematch_required` 可在本 subgraph 内以新 intent snapshot 受控循环。

## 7. 测试要求

### 7.1 单元测试

- qualification operator 与 overall hard status 真值表。
- capability level、ontology exact/transfer/unmapped 对齐。
- weight、分子、分母、null coverage 和 unknown exclusion。
- 四类 Gap 正反例与 unknown 不误判 capability gap。
- preference hard/negotiable 分离和单位不可比较。
- stable ranking、tie-breaker 和 failed 结果保留。
- snapshot ownership/version/staleness 校验。
- LLM fact/citation/action validator 和 deterministic fallback。
- reducer、budget、idempotency 和 secret/PII 日志边界。

### 7.2 集成测试

- v0.4 candidate fixture + v0.5 job fixture → assessment → comparison → interrupt。
- select/defer/reject resume 与 TargetDecision 持久化。
- candidate correction → `candidate_profile_required`。
- negotiable preference update → 新 intent → rematch，不调用 role research。
- city/role/hard scope update → `role_research_required`。
- stale/expired role → `role_refresh_required`。
- SQLite checkpoint 进程重启和重复 response replay。
- v0.1-v0.5 全量回归。

## 9. 验收标准

v0.6 只有同时满足以下条件才可标记 Implemented / Accepted：

1. Requirements、RFC、ADR、State、Human Interaction、LLM 和 Matching contracts 已同步。
2. 四类 gap、资格状态和覆盖公式均有 schema、规则与固定集测试。
3. 所有明确失败和已满足结果可追溯双方 Claim；unknown 从不被当作明确失败。
4. 多岗位稳定比较不产生 Offer 概率或不透明综合分。
5. 用户可 select/defer/reject，并能从 interrupt 跨进程恢复且重复 resume 幂等。
6. 候选人纠正只路由 v0.4；同 scope 偏好更新只 rematch；SearchScope 变化只路由 v0.5。
7. 输入快照变化会使旧 assessment/comparison 失效并生成新版本，不原地覆盖历史。
8. LLM 非法输出不会改变确定性事实，provider 不可用时仍能输出完整比较结果。
9. v0.6 新增测试和 v0.1-v0.5 全量回归全部通过。
10. 新增 `docs/07_evaluation/v0.6-eval-report.md`，离线指标与可选 live smoke 分开展示。

## 10. 文档完成后实现顺序

2. deterministic qualification/capability/preference evaluator；
3. assessment/comparison projector 与 stable ranking；
4. matching subgraph、checkpoint 和 report；
5. human decision、intent impact 和 rebuild directive；
6. LLM explanation 与 validator/fallback；
7. fixture、集成测试、Eval 和可选 DeepSeek smoke。
