# v0.7 准备计划与反馈闭环需求

状态：Implemented / Accepted
日期：2026-07-27
关联 ADR：`docs/05_adr/0007-evidence-first-feedback-and-deterministic-preparation.md`
关联 RFC：`docs/04_rfc/0007-preparation-plan-and-feedback-loop.md`

## 1. 背景

v0.6 已将 CandidateProfile、CareerIntent 和具体岗位画像转换为可解释的资格、能力证据覆盖、
偏好与不确定性结果，并允许用户选择、暂缓或拒绝岗位。下一步不是追求“把所有 gap 清零”，
而是根据用户真正选择的岗位、可用时间和岗位截止日期，形成有限、可执行、可验证的准备计划。

计划执行后还会产生新的练习、笔试、面试、申请和用户复盘反馈。这些反馈既可能证明候选人能力，
也可能只表示一次任务进度、某个具体岗位的考察信号，或仅是无法归因的结果。如果系统把一次拒绝
直接解释成能力不足，或把一次面试问题提升为整个岗位族的普遍要求，就会污染已有画像和后续计划。

v0.7 因此需要建立两个独立但可串联的 subgraph：

- `preparation_plan`：从已选择岗位及带证据的差距生成最小准备包、任务优先级和可行排期；
- `feedback`：先归档反馈，再分离 observation 与 diagnosis，确认作用域，输出画像重建/重匹配/
  重排计划指令。

## 2. 目标

实现以下闭环：

```text
selected TargetDecision(s)
Candidate / Intent / Role snapshots
GapAssessment(s) + hiring signals
PreparationConstraints
  → 校验输入版本和用户选择
  → 生成有引用的准备目标与候选活动
  → 确定性优先级分层、依赖校验和容量排期
  → MinimumPreparationPackage + LearningPlan snapshot
  → 用户审阅 interrupt
  → 接受 / 调整时间与活动 / 暂缓 / 取消

practice / written exam / interview / application / reflection feedback
  → raw-before-interpret 归档
  → Observation / Diagnosis 分离
  → scope、authority、confidence 与冲突校验
  → 高影响归因用户确认 interrupt
  → EvidenceClaim(feedback_signal)
  → FeedbackImpactAssessment
      ├─ 仅更新任务进度
      ├─ 请求 CandidateProfile 重建
      ├─ 请求 RoleProfile 核验/聚合候选
      ├─ 请求 Intent review / rematch
      └─ 请求 LearningPlan 重排
  → 新 snapshot 回传后生成新的 LearningPlan，旧计划 superseded
```

## 3. 范围

### 3.1 必须实现

- 独立 `preparation_plan` LangGraph subgraph。
- 独立 `feedback` LangGraph subgraph。
- `PreparationInputSet`、`PreparationConstraints`、`PreparationObjective`、
  `PreparationActivity`、`PriorityFactors`、`MinimumPreparationPackage`、`LearningPlan` 契约。
- `FeedbackEvent`、`FeedbackObservation`、`FeedbackDiagnosis`、`FeedbackAttribution`、
  `FeedbackImpactAssessment` 和 `FeedbackDirective` 契约。
- 只为 v0.6 当前 `selected` TargetDecision 构建计划；deferred/rejected 目标不进入计划分母。
- 基于岗位重要性、GapType、hiring signal、跨目标迁移价值、可提升性、截止时间和成本的
  确定性优先级 policy。
- 容量约束、依赖 DAG、任务截止日期和 stable scheduling。
- 最小准备包：满足明确 policy 和用户容量即可，不要求 CandidateProfile 与 RoleProfile 100% 相等。
- 对无法在当前时间窗口解决的硬性阻塞项显式标记 `unaddressable_blocker`，不得伪造学习任务。
- deterministic baseline activity generator；可选 LLM 只负责活动拆解、说明和反馈结构化候选。
- `review_preparation_plan` 和 `confirm_feedback_attribution` interrupt/resume。
- 用户反馈先成为 Artifact/Fragment，再形成 observation/diagnosis/Claim；State 不保存长期正文。
- observation、diagnosis、outcome 和用户自述分离；无明确反馈的拒绝不得推断原因。
- FeedbackImpact policy 与跨域 directive；v0.7 不直接覆盖 Candidate/Role/Intent snapshot。
- 外部 rebuild/rematch 完成后，以 resolved snapshot refs 恢复并重排计划。
- SQLite checkpoint、不可变计划版本、stale/supersede、幂等、预算、trace、report 和 Eval。
- 保留 v0.1-v0.6 全量回归。

### 3.2 最小准备包

`MinimumPreparationPackage` 是确定性计划策略的结果，不是“可拿 Offer”认证。首版必须包含：

- 当前窗口内可处理的申请硬阻塞项；
- 为达到配置化核心证据覆盖目标所需的最小活动集合，或在容量不足时的最大价值子集；
- 被选岗位要求的必需申请材料活动；
- 对有足够 scope/authority 的 frequent hiring signal 至少一个对应练习；
- 能显著改变投递判断且成本可控的高价值 uncertainty resolution；
- 所有无法处理、容量不足而未排入、依赖阻塞和 unknown 项的明确列表。

覆盖目标用于选择计划活动，不表示用户达到 Offer/面试概率。若硬性资格本身不可改变，计划应建议
重新审阅目标，而不是生成虚假的“补学历/改毕业年份”任务。

### 3.3 反馈作用域

反馈必须先归为以下 scope 之一：

```text
plan_task
candidate_capability
candidate_evidence
job_instance
company_role
role_family_candidate
career_intent
unknown
```

- `plan_task`：只证明任务进度，不自动证明能力等级变化。
- `candidate_capability/evidence`：可形成反馈 Claim，并请求 v0.4 重建 CandidateProfile。
- `job_instance/company_role`：只能形成对应范围的 hiring/experience signal，不能创建官方 hard requirement。
- `role_family_candidate`：单次事件只能作为待聚合候选，必须由 v0.5 独立来源/样本 policy 决定是否进入岗位族画像。
- `career_intent`：只触发 intent review，不修改候选人能力。
- `unknown`：保留反馈，但不产生画像事实修改。

### 3.4 非目标

- 不承诺“学完即可投递/通过面试/获得 Offer”。
- 不根据一次失败或拒绝自动诊断能力原因。
- 不把任务完成状态直接等同于能力已掌握。
- 不让单次面试、单个用户或单一公司反馈改写 RoleFamilyProfile 的 common/frequent requirement。
- 不在 v0.7 自动执行 v1.0 Parent Graph；跨图修改通过 directive 和 resume refs 协调。
- 不提供全网课程搜索、外部资源推荐、Hybrid RAG 或向量检索；这些属于 v0.8。
- 不实现自动投递、邮件、日历写入、Web UI、分布式存储或 Multi-Agent。
- 不让 LLM 自由决定 priority、schedule、能力升级、岗位事实或反馈因果关系。

## 4. 输入与输出

### 4.1 Preparation 输入

- `run_id`、`thread_id`、`user_id`。
- 1..N 个当前 `selected` TargetDecision ID。
- 对应的 ComparisonSet、GapAssessment 和具体岗位 snapshot ID。
- CandidateProfile、CareerIntent 和可选 RoleFamilyProfile snapshot ID。
- `PreparationConstraints`：开始/结束日期、每周可用小时、单日上限、不可用日期、活动偏好。
- 可选历史 LearningPlan、完成状态和已归档 feedback refs。
- plan、LLM、interaction 和 replan 预算。

### 4.2 Preparation 输出

- 不可变 `PreparationInputSet`。
- `PreparationObjective` 和候选 `PreparationActivity` 列表。
- 每项活动的 `PriorityFactors`、priority band、依赖、工时、截止日期和 supporting refs。
- `MinimumPreparationPackage`。
- 一个版本化 `LearningPlan` snapshot。
- 用户审阅结果、未排入项、unaddressable blockers、warnings、trace 和 report。

### 4.3 Feedback 输入

- feedback type、发生时间、关联 target/plan/task/stage refs。
- 用户输入文本、本地文件或结构化结果；文件路径必须在授权范围内。
- 可选 evaluator/platform/official outcome metadata。
- 当前 plan 和相关 profile/comparison snapshot refs。
- resume 时的 attribution confirmation 或 resolved rebuild refs。

### 4.4 Feedback 输出

- `FeedbackEvent`、Artifact/Fragment IDs。
- 0..N 个 observation、diagnosis 和 attribution。
- 0..N 个经过验证的 `EvidenceClaim(claim_type=feedback_signal)`。
- `FeedbackImpactAssessment` 和 0..N 个 `FeedbackDirective`。
- 可选任务进度事件、新 Candidate/Role/Intent/Comparison snapshot refs 和新版 LearningPlan ID。
- 状态：`completed`、`completed_with_unknowns`、`interrupted`、`reroute_required`、
  `awaiting_rebuild`、`cancelled` 或 `failed`。

## 5. 功能要求

### FR-01 Preparation 输入与版本校验

- TargetDecision 必须属于当前 user，状态为 selected，并引用 current/允许继续使用的 ComparisonSet。
- 所有 GapAssessment 和 RoleProfile 必须与 decision 的 job snapshot 对应。
- 一个计划固定引用 exact candidate、intent、comparison、gap、role、decision 和 policy version。
- 任一业务输入更新后旧 plan 标 `stale`；确认重排后新 plan supersede 旧版本。
- 没有 selected target 时返回 `target_selection_required`，不得生成通用学习清单。

### FR-02 PreparationConstraints

- 必须包含明确 horizon 和 capacity；默认值也必须写入 snapshot，不能隐藏在 prompt。
- `weekly_hours >= 0`，单日/单周容量、不可用日期和 timezone 由代码校验。
- 用户可声明活动类型偏好或禁用类型，但不能借此改变岗位事实或 GapType。
- 修改 constraints 只重排/重建计划，不修改 Candidate/Role/Intent。

### FR-03 Objective 与活动候选

- 每个 objective 必须绑定至少一个 gap、requirement、qualification、hiring signal 或 application asset。
- 活动类型至少包括：`resolve_uncertainty`、`strengthen_evidence`、`develop_capability`、
  `prepare_application_asset`、`written_exam_practice`、`interview_practice`、
  `portfolio_revision`、`target_review`。
- 每项 activity 必须有完成定义、预期产物、验证方式、估计工时、supporting refs 和安全边界。
- 活动不得声称完成后能力等级必然提升；需要新证据后由 CandidateProfile projector 判断。
- 没有现有来源支持的外部课程/链接不得由模型编造。

### FR-04 确定性优先级

- priority band：`P0_blocker`、`P1_core`、`P2_transferable`、`P3_bonus`、`P4_deferred`。
- band 由明确规则生成；band 内稳定排序依次使用：
  1. 受影响 selected target 数量；
  2. requirement effective weight / hard blocker；
  3. hiring signal authority、scope 和独立来源数；
  4. transfer value；
  5. deadline urgency；
  6. improvability；
  7. estimated effort 升序；
  8. stable activity ID。
- 所有 factors、归一化值、reason code 和 policy version 必须输出。
- LLM 不能改变 band、factor、排序或依赖。

### FR-05 Hiring signal 使用边界

- job_instance/company_role signal 只影响相应 target 的准备活动。
- role_family signal 只有在 v0.5 已标 frequent 且样本门槛满足时才能提高跨目标优先级。
- 单一 observed signal 可生成低优先级练习候选，但不得称为“必考”。
- historical/unknown freshness 降低信息价值并产生 warning，不自动删除。

### FR-06 容量、依赖和排期

- activity dependencies 必须形成 DAG；循环依赖拒绝计划发布。
- scheduler 不得超过 horizon、weekly/daily capacity 或 activity deadline。
- 不可拆分活动按完整工时安排；可拆分活动声明最小 session。
- 容量不足时按 policy 选择最大价值子集，未排入活动保留 deferred reason。
- stable input 和 policy 必须产生相同 schedule。

### FR-07 MinimumPreparationPackage

- package 保存 included/deferred/unaddressable activity IDs 和各目标覆盖摘要。
- addressable hard blocker 优先；unaddressable hard blocker 必须触发 `target_review`。
- 核心 coverage target、最小 practice 数和 application asset 要求均为版本化配置。
- package 可因容量不足标 `partial`，不能降低门槛后伪装 complete。
- status：`complete`、`partial`、`blocked`、`unknown`，只描述计划包，不描述 Offer readiness。

### FR-08 LLM 计划边界

- 模型只接收已校验 planning facts、允许活动类型、用户 constraints 和事实引用。
- LLM 可提出 activity wording、拆解、完成定义和估计工时候选。
- validator 必须校验所有 gap/target/signal/claim refs、活动类型、依赖和工时范围。
- priority、schedule、package status 和最终估计由确定性 policy 裁决。
- 模型失败时使用 deterministic activity templates，Graph 仍可完成。

### FR-09 计划审阅与版本

- `review_preparation_plan` 展示输入 refs、package status、活动、排期、deferred 和 blockers。
- allowed actions：`accept_plan`、`revise_constraints`、`exclude_activities`、
  `request_activity_revision`、`defer_plan`、`cancel`。
- 用户不能通过 response 改写 requirement/gap/priority facts；只能改变 constraints 或活动呈现。
- 合法修改生成新 plan version，旧 plan superseded；重复 resume 幂等。

### FR-10 Feedback raw-before-interpret

- 任何反馈文本、文件、结构化结果先保存 immutable Artifact，再解析 Fragment。
- metadata 保存 feedback type、发生时间、stage、source kind 和关联 refs，不保存密钥。
- 解析失败仍保留 Artifact，并以 unknown 完成或请求支持格式。
- 同一内容/事件使用 canonical hash 幂等复用。

### FR-11 Observation 与 Diagnosis 分离

- Observation 只表达材料明确出现的行为、问题、分数、评价、结果或用户自述。
- Diagnosis 是从 observation 到潜在能力/证据/岗位信号的推断，必须显式 `model_inference` 或待确认。
- `rejected/failed/no_offer` 且没有明确评价时只记录 outcome，不允许生成能力 diagnosis。
- 用户复盘只能作为 user_reported，不提升为 evaluator/official observation。
- 每个 diagnosis 必须引用 observation IDs、confidence、alternative explanations 和 limitations。

### FR-12 Feedback 归因与人工确认

- scope、subject、capability、job/stage 和 authority 均由 validator 校验。
- 影响 Candidate/Role/Intent 的高影响 attribution 必须通过 `confirm_feedback_attribution`。
- allowed actions：`confirm_attributions`、`relabel_scope`、`reject_diagnoses`、
  `mark_unknown`、`cancel`。
- 用户确认 diagnosis 只把它变成 user-confirmed inference，不改变原始来源 authority。
- 校验失败或用户拒绝时保留 observation，diagnosis rejected/unknown。

### FR-13 Feedback Claim 与影响路由

- accepted observation/diagnosis 生成 `feedback_signal` Claim，并精确引用 Fragment。
- task progress 可写 PlanProgressEvent；除非有独立能力证据，不触发 CandidateProfile 升级。
- candidate scope → `candidate_profile_rebuild_required`。
- job/company scope → `role_instance_refresh_required`，以 signal_only/experience authority 进入 v0.5。
- role family candidate → `role_family_aggregation_candidate`，单次反馈不得直接更新聚合画像。
- intent scope → `intent_review_required`。
- 任何 matching 输入变化后 → `rematch_required`；任何 relevant gap/constraints/progress 变化后 → `replan_required`。

### FR-14 外部重建与闭环恢复

- Feedback Graph 只发出 directive，不直接跨域覆盖 snapshot。
- application service 执行现有 v0.4/v0.5/v0.6 边界后，以 directive ID 和新 snapshot refs resume。
- resume 必须验证 refs 属于同 user、确为旧 snapshot 后继版本且满足 directive 类型。
- 新 snapshot 到达后旧 plan 标 stale，Preparation Graph 生成新版本并保存 change explanation。
- 一个固定集验收必须完成“反馈 → Candidate snapshot 更新 → rematch → plan reorder”的真实本地闭环。

### FR-15 Checkpoint、幂等与预算

- 两个 subgraph 均使用 SQLite checkpointer 和独立 thread ID。
- activity、plan、feedback event、observation、diagnosis、claim、progress、directive 使用稳定幂等键。
- 默认预算：`max_plan_rounds=3`、`max_activities=30`、`max_llm_calls=12`、
  `max_plan_interrupts=3`、`max_feedback_items=20`、`max_feedback_interrupts=3`。
- 达到预算后保留 unknown/deferred，以合法终态停止。

### FR-16 Trace、Report 与隐私

- trace 记录 ID、factor、route、schedule count、scope、authority、directive 和错误摘要。
- plan report 展示 package、活动、排期、依赖、deferred、blocker 和 evidence refs。
- feedback report 展示 observation/diagnosis 分离、确认状态、影响和新版本链。
- 不复制完整面试记录、私人评价、完整简历、Cookie 或 API key。
- 报告明确说明计划优先级不是成功概率，反馈诊断也不是确定因果结论。

## 6. Graph 行为

### 6.1 Preparation Plan Graph

```text
START
  → initialize_preparation_run
  → load_and_validate_selected_targets
  → derive_preparation_objectives
  → generate_activity_candidates
  → validate_activity_candidates
  → compute_priority_factors
  → build_minimum_preparation_package
  → schedule_activities
  → project_learning_plan
  → route_plan_next_action
      ├─ review_user → plan_review_interaction
      │                 → interrupt_for_plan_review
      │                 → validate_plan_review
      │                 ├─ accept → finalize_plan
      │                 ├─ revise → plan loop
      │                 ├─ defer/cancel → finalize_plan
      │                 └─ invalid → fail
      ├─ complete/partial/blocked → finalize_plan
      └─ fail → finalize_plan
```

### 6.2 Feedback Graph

```text
START
  → initialize_feedback_run
  → ingest_and_archive_feedback
  → extract_feedback_observations
  → propose_feedback_diagnoses
  → validate_feedback_attributions
  → route_feedback_confirmation
      ├─ high impact → plan_attribution_interaction
      │                 → interrupt_for_attribution
      │                 → validate_attribution_response
      └─ observation/progress only
  → persist_feedback_claims_and_progress
  → assess_feedback_impact
  → build_feedback_directives
  → route_feedback_next_action
      ├─ progress only → finalize_feedback
      ├─ rebuild required → await_external_rebuild
      │                      → resume with resolved refs
      │                      → validate_rebuild_resolution
      │                      → request rematch/replan
      └─ complete_with_unknowns/fail → finalize_feedback
```

v0.7 不实现长期常驻等待。每次 plan 创建或 feedback 摄取是有界 run；未来 Parent Graph 负责跨 run
串联，v0.7 验收使用 application service/saga 模拟相同 directive/resume 边界。

## 7. 测试要求

### 7.1 单元测试

- preparation/feedback schema、canonical hash 和 repository。
- priority band 与 stable ordering 真值表。
- minimum package inclusion/deferred/unaddressable 规则。
- scheduler capacity、deadline、splitting 和 dependency cycle。
- hiring signal scope/authority/freshness。
- observation/diagnosis/outcome 分离。
- feedback scope、authority、confidence 和 alternative explanation。
- rejection-without-feedback 零能力 diagnosis。
- single-event role-family mutation guard。
- plan/feedback reducer、budget、stale、supersede 和幂等。
- LLM invalid refs/priority/causality rejection 与 deterministic fallback。

### 7.2 集成测试

- v0.6 selected decisions → plan → review interrupt → accepted LearningPlan。
- constraints revision → new feasible plan version。
- capacity shortage → partial package + deferred tasks。
- unaddressable blocker → blocked/target review。
- feedback text/file raw-first → observations → attribution interrupt。
- task completion只更新 progress。
- explicit mock interview feedback → feedback Claim → candidate rebuild directive。
- interview rejection无原因 → outcome only。
- job-specific question → role instance signal directive。
- single event不修改 role family。
- SQLite checkpoint restart 和 duplicate response/event replay。
- feedback → new candidate snapshot → rematch → plan reorder 的本地闭环。
- v0.1-v0.6 全量回归。

## 9. 验收标准

v0.7 只有同时满足以下条件才可标记 Implemented / Accepted：

1. Requirements、RFC、ADR、Preparation/Feedback Contracts、State、Human、LLM、Tool、Evidence 和 Eval 已同步。
2. selected target 能生成容量可行、有依赖、有完成定义和引用的 MinimumPreparationPackage。
3. priority 和 schedule 可重放；LLM 不能修改确定性 factors、band 或排期。
4. 容量不足、硬阻塞不可处理和 unknown 均诚实展示，不伪造完整计划。
5. feedback raw-before-interpret，observation/diagnosis/outcome 明确分离。
6. 无明确评价的拒绝不产生能力 diagnosis；任务完成不自动升级能力。
7. 单次反馈不直接改写 RoleFamilyProfile，所有跨域变化通过证据和 directive。
8. plan/feedback interrupt 可跨进程恢复，重复 resume/event 幂等。
9. 至少一个固定集完成反馈证据 → Candidate snapshot → rematch → plan reorder 的版本链。
10. v0.7 新增测试和 v0.1-v0.6 全量回归全部通过。
11. 新增 `docs/07_evaluation/v0.7-eval-report.md`，离线指标与可选 DeepSeek smoke 分开展示。
