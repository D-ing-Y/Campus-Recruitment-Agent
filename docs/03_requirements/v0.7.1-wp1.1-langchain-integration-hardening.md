## 1. 当前问题

WP1 已用真实 DeepSeek 完成 Candidate 纵向验收，但接入层仍存在架构债务：

- `OpenAICompatibleProvider` 手写 HTTP Chat Completions，只使用 `json_object`，没有利用供应商原生
  JSON Schema、Tool Calling、标准消息对象、能力描述和统一错误边界；
- `ToolRegistry` 只有 `name + run(dict)`，缺少模型可见描述、输入 JSON Schema、调用 ID、暴露策略和
  LangChain `BaseTool` 适配；
- 项目没有 MCP Client/Server 配置与适配边界，外部工具无法按统一协议进入受控 Agent 节点；
- “LangChain Structured Output 支持”和“Provider-native Structured Output”没有在运行记录中区分，
  容易把 Tool Calling 或 JSON Mode 误报为原生 Schema；
- 单一 `openai_compatible` 配置掩盖 DeepSeek、OpenAI-compatible 等集成的能力差异。

## 2. 目标

1. 保留现有 LangGraph、State、Evidence、Validator、Projector、Repository、CLI 与 Run Artifact。
2. 用 LangChain provider integration 替换生产运行时的手写模型 HTTP 路径；旧类只保留兼容测试边界。
3. 建立 `ModelCapabilities` 与 `StructuredOutputGateway`，按能力选择：

   ```text
   provider_native_json_schema
     → strict_tool_calling / tool_calling
     → json_mode + local validation
     → explicit unsupported/failure
   ```

4. 结构化结果必须继续经过 Pydantic 和领域 Validator；供应商 Schema 不能替代 Evidence 约束。
5. 为内部 Tool 建立显式 `ToolSpec`，并可安全适配为 LangChain Tool；默认 `internal_only`。
6. 建立 MCP Client 配置、加载和 LangChain Tool 转换边界，使获准外部资源可进入有限 Agent 节点。
7. 旧 Model Provider SQLite 记录和本地 secret ref 必须可继续读取，API key 不进入 State、日志或 MCP 配置。
8. 运行记录必须展示实际 structured-output strategy，而不是只记录 provider/model。

## 3. 非目标

- 不把全部 Workflow 改写为 `create_agent()`。
- 不让 LLM 决定 Claim 接受、Profile 投影、评分、路由、数据库写入或权限扩大。
- 不把 Repository、Checkpointer、CredentialStore 或确定性 Validator 暴露为模型 Tool/MCP Tool。
- 不在本工作包实现 v1.0 Parent Graph、Multi-Agent、Web UI 或新的业务 Workflow。
- 不要求本地纯函数或单进程内部 Tool 全部 MCP 化。
- 不在 CLI 中提前开放 MCP 配置页面；本轮提供版本化配置/装配接口和测试入口。
- 不把外部 MCP 可连接等同于外部来源真实可用；真实来源仍按 WP3 E5 门禁验收。

## 4. 目标架构

```text
CLI / RuntimeFactory
  → LangGraph workflow
      → deterministic node/service
      → bounded LLM node
          → StructuredOutputGateway
              → LangChainChatProvider
                  → ChatDeepSeek / ChatOpenAI-compatible
      → bounded tool node/agent
          → ToolCatalog
              → local ToolSpec → LangChain BaseTool
              → MCP server → langchain-mcp-adapters → BaseTool
  → Evidence / Validator / Projector / Repository
```

## 5. 强制边界

### 5.1 模型边界

- Provider 配置必须携带或可推导 integration 与 capability；旧 DeepSeek profile 按 URL/model 安全迁移。
- `deepseek-chat` 使用 Tool Calling structured output；不得标记为 provider-native JSON Schema。
- DeepSeek 当前 endpoint 的 Thinking 默认开启；强制 `tool_choice` 的结构化调用必须由
  Provider adapter 显式关闭 Thinking，不得依赖 Prompt 规避协议冲突。
- `deepseek-reasoner` 未确认 Tool Calling 时必须显式拒绝该 strategy，不静默降级成成功。
- 每次调用记录 `requested_strategy`、`effective_strategy`、`capabilities` 和 fallback reason。
- raw response 只进入受控 cache/receipt；API key、Authorization 和完整私人材料不进入诊断产物。

### 5.2 Tool 边界

- Tool 输入使用 Pydantic/JSON Schema，不再以无描述 `dict[str, Any]` 直接暴露给模型。
- `internal_only` 是默认值；只有 allowlist 中的 `model_read`/`model_action` Tool 可绑定模型。
- 有副作用 Tool 必须声明 side effect、授权与幂等要求；高风险动作需要 Human Gate。
- LangChain Tool 返回必须重新包装为项目 `ToolResult`/Artifact refs，不能绕过既有事实存储。

### 5.3 MCP 边界

- MCP 配置只保存 server id、transport、command/args 或 URL、credential ref，不保存 secret value。
- 只允许 `stdio` 与 `streamable_http/http`；SSE 仅兼容读取，不作为新增默认。
- MCP tools 必须经过 server allowlist、tool allowlist、命名冲突、schema 和 exposure policy 检查。
- MCP tool output 是外部输入，必须视为不可信内容；进入业务层前仍走 raw/evidence/validator。
- MCP 不得获得 Graph State、Repository 或 SecretStore 的任意访问权；需要上下文时通过最小 interceptor 注入。

## 6. 兼容迁移

- `ModelProviderProfile` 既有 JSON/SQLite 记录继续有效；缺失 integration/capability 时确定性推导并在安全输出中展示。
- 现有 `LLMProvider` protocol 暂保留为业务隔离边界，新增 LangChain adapter 实现，业务节点不直接依赖厂商 SDK。
- 现有 `ToolRegistry.run()` 保持兼容；新增注册元数据和 LangChain Tool 导出，不一次性改写全部 Tool。
- 现有 cache key 至少增加 effective strategy/capability fingerprint，避免 JSON Mode 与 Tool Calling 复用错误缓存。

## 7. 验收条件

- DeepSeek active profile 由 `ChatDeepSeek` 装配，旧配置无人工迁移即可运行。
- custom OpenAI-compatible profile 由 `ChatOpenAI` 兼容装配，不再走手写 HTTP 生产路径。
- Claim 提取成功记录 `tool_calling`，离线回放保持同一业务结果。
- 原生 Schema mock/adapter、Tool Calling、JSON fallback 和 unsupported 四条策略均有测试。
- ToolSpec 非法/未授权/重复名称在绑定模型前拒绝。
- 至少一个本地 MCP fixture server 能被加载为 LangChain Tool；未知 server/tool 被拒绝。
- MCP/tool 输出不能直接写 Profile，不能泄漏 API key，不能绕过 ValidationReceipt。
- 全量回归、Candidate E0-E4 重跑通过后才把 WP1.1 标记 Passed；WP2 仍不得提前开始。
