# v0.7.1 WP3.1 岗位需求与评价画像分流

状态：WP3.1.1 Implemented / Offline Verified / Multi-platform Live Pending
日期：2026-08-11
关联 RFC：`docs/04_rfc/0015-split-role-demand-and-reputation-workflows.md`
关联 ADR：`docs/05_adr/0015-use-platform-detail-as-default-and-split-role-intelligence.md`、
`docs/05_adr/0016-use-bounded-community-search-and-external-social-sidecar.md`
关联 Contract：`docs/06_contracts/role-demand-reputation-contract.md`

## 1. 背景与问题

WP3 已离线实现多 SearchScope、RoleFamilyMembership、RoleDetailEvidenceReceipt 和
ExperienceScopeLink，但尚有四个顶层设计问题：

1. 企业官网核验仍在 RoleProfileGraph 主路径上，使每个公司都可能需要单独适配，
   成本和失败面随公司数增长。
2. `JobInstanceRoleProfile.hiring_signals` 同时承载面试经验、技术偏好、薪资和工作体验，
   不同用途的主观证据被混合。
3. 现有 experience channel 没有明确区分“招聘面经”与“在职体验评价”，两类信息可能
   被错用为能力要求或公司风评。
4. 缺少 company-level 评价画像。岗位级信号无法经过范围校验后为多岗位共享，
   用户也无法分别“这个岗位如何”和“这家公司如何”。

## 2. 设计目标

- 招聘平台的真实岗位详情页 Raw Artifact 足以启动岗位需求画像，不再强制二次官网核验。
- 官网/官方 ATS 保留为条件触发的证据升级通道，不是每个岗位的完成条件。
- 将岗位情报投影为彼此独立的 Demand 和 Reputation，保留共同原始证据层。
- 在岗位检索后建立 company → role family → job cluster 范围，用于生成有界的社区查询。
- 将面经转化为面试/笔试准备信号，将在职体验转化为岗位/公司评价信号。
- 不将主观评价投影为 hard requirement，也不将单篇面经描述为“必考”。

## 3. 来源边界

### FR-01 招聘平台默认主路径

- search page/card 仍只用于 discovery，不得直接生成 Demand Profile。
- adapter 必须进入该平台的具体 job detail，归档 Raw Artifact 并生成 `job_detail`
  SourceDocument 后才可通过 RoleDetailEvidenceReceipt。
- recruitment platform detail 对岗位标题、公司、地点、职责、任职要求和平台展示薪资
  为 `allowed` 且足以投影，但仍保留来源、检索时间、冲突和过期风险。
- 不把“平台展示”提升为“永久官方真相”，不因省略官网核验而丢失 freshness 和
  conflict 语义。

### FR-02 官方来源改为可选升级

Role run 正常完成时 `mandatory_official_verification_count` 必须为 0。仅在以下情况创建
OfficialVerificationPlan：

- 不同招聘平台对关键字段存在真实冲突；
- 岗位似乎过期、关闭或申请入口不可用；
- 平台详情缺失核心字段或证据质量不足；
- 用户已将该公司/岗位标记为高优先级并显式要求核验。

官方升级使用通用 allowlist/ATS adapter 或 `adapter_required`，不以“为每家公司编写代码”
作为 WP3 验收要求。

## 4. 画像分流

### FR-03 Demand Profile

Demand 包含两个明确分区：

- `jd_requirements`：资格、职责、核心能力、加分项、工作上下文，只由招聘详情或可选官方证据生成。
- `assessment_signals`：面试阶段、提问主题、笔试范围、项目偏好和反馈，只由 interview evidence
  生成，始终标记 `observed/frequent/insufficient_sample`。

Demand 分为 `JobDemandProfile` 和 `RoleFamilyDemandProfile`。前者用于具体 JD gap，后者用于
大类岗位通用能力和学习最小包。

### FR-04 Reputation Profile

- `JobReputationProfile` 仅聚合可明确绑定 company-role/job-instance 的 employment evidence。
- `CompanyReputationProfile` 可聚合同一 company 不同岗位的 company-scoped employment evidence，
  但必须保留岗位分布、样本数、时间窗和冲突。
- 评价维度至少包含 work intensity、management、team atmosphere、compensation、growth、
  stability 和 work content。
- 单一来源只能形成 anecdotal/observed signal，不得生成公司整体事实或综合分数。
- LLM 可生成带限制的 `overall_summary`，不得修改样本数、维度结论、冲突和引用。

## 5. 社区检索与证据分类

### FR-05 CompanyRoleGroup 与有界查询

招聘岗位去重后按 `company_key + role_family` 建立 CompanyRoleGroup。每个用途由确定性策略逐轮
生成查询，LLM 不得决定放宽、切换来源或停止：

1. `公司 + 代表性完整岗位名 + 面经/工作体验`；
2. `公司 + 规范化岗位族展示名 + 面经/工作体验`；
3. `公司 + 面经/工作体验`。

面经来源优先级固定为牛客、小红书；工作体验固定为小红书、牛客。每个来源、每个用途最多三轮；
累计获得两篇按 canonical URL、平台帖子 ID 和正文 hash 去重后的合格详情文档即提前停止。主来源
三轮结束或被阻断后切换备用来源；两个来源均不足时显式发布 `partial/blocked`，不得用摘要补足。

每个 query 必须保存 `evidence_purpose`、`round_index`、`relaxation_level`、`parent_query_id`、
`source_priority`、parent group、预算和来源回执。内部 family ID 只能通过岗位族展示词典转换后进入
检索词，禁止直接发送给第三方来源。

查询词只负责发现候选，不能证明帖子作用域。详情正文明确出现完整岗位名时才可绑定
company-role，明确出现岗位族时才可绑定 role-family，只出现公司时只允许 company scope；公司或
岗位归属无法确认的内容不得进入 Demand 或具体岗位 Reputation。company-only 评价不得自动归属
为某个具体岗位的体验。

最坏搜索上限为每个 CompanyRoleGroup `2 用途 × 2 来源 × 3 轮 = 12`，并继续受全局文档、
详情、Tool Call 和模型调用预算约束。

### FR-06 文档级与片段级分类

- 社区详情页先归档，再分类为 `interview_experience | employment_experience | mixed | unknown`。
- `mixed` 必须拆成带独立 Fragment/quote 引用的 typed segments，不能整篇同时投影到两个画像。
- 无可定位原文、scope ambiguous 或 segment type unknown 时保留证据，不进入任何画像。
- LLM 只负责 typed extraction/summarization；Validator 校验 quote、scope、usage 和严格输出结构。

## 6. 下游消费边界

- Matching/GapAssessment 只使用 Demand 的 qualification/requirement，Reputation 不得生成能力 Gap。
- TargetDecision 可同时展示 Demand 匹配和 Reputation 参考，但用户选择不得改写客观画像。
- Preparation 使用 Demand 的 requirements 和 assessment signals，不使用 work intensity/atmosphere 生成学习任务。
- 具体岗位问答通过 RoleIntelligenceBundle 读取 Demand、Reputation 和 Raw evidence refs，
  回答必须显式区分 JD 事实、面经信号和主观评价。

## 7. 非目标

- 不为每家公司生成或执行任意爬虫代码。
- 不建立完整公司实体知识图谱；`company_key` 仅做本地规范化和可审计别名。
- 不使用单一综合分数排名公司，不预测 Offer/入职体验。
- live 采集保持显式 opt-in；离线实现完成不等于多平台 live accepted。
- 不把 MediaCrawler 源码复制、修改或发布到本仓库；其非商业学习研究许可证由本地操作者确认。
- 不开放评论、二级评论、创作者遍历、代理池、发布能力或绕过登录/验证码/风控的行为。
- MediaCrawler 上游支持的其他平台不自动获得准入；首版只准入小红书。

## 8. 验收标准

- 无官网数据但有有效平台 job detail 时，Demand Profile 可发布且保留来源限制。
- search card 仍不得生成 Demand Profile。
- interview segment 进入 assessment signals 但不进入 Reputation。
- employment segment 进入 Reputation 但不进入 qualification/requirement/assessment signal。
- mixed document 的每个已投影结论都可追溯到自己的 quote Fragment。
- company-only signal 可进入 CompanyReputationProfile，不进入任一 JobReputationProfile。
- 多岗位公司画像保留 role distribution，不用某一岗位的工作体验代表全公司。
- Matching/Preparation 的证据输入不受 Reputation 污染。
